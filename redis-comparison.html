VeltrixDB vs Redis — when RAM stops scaling.

Redis is excellent software. But when the keyspace outgrows RAM, the memory bill compounds and fork-based persistence shows up in the tail. Here is where each one wins — with every VeltrixDB number labelled as measured, internal or calculated.

SS
Shubham Sharma
Founder · VeltrixDB
Published · May 2026 Read time · 12 minutes Updated · Sep 2026 · v1.8
01
The core difference

Redis keeps everything in RAM. VeltrixDB doesn't have to.

Redis's speed comes from one thing: all data lives in memory. That's a real advantage — and a real cost ceiling. VeltrixDB keeps only the index and a LIRS cache in DRAM and stores values on NVMe, so hot keys are answered from memory and cold data is priced like disk, not like RAM.

This is not a "Redis killer" comparison. Redis is the right choice for millions of workloads. But there is a specific class of problem — large keyspaces under sustained write pressure — where keeping every byte in RAM, and forking to persist it, gets expensive and noisy.

When Redis is under heavy write load, the fork behind an AOF rewrite or RDB save can make P99 spike. Engineers work around this with replica reads, fork tuning and alert rules. VeltrixDB does not fork to persist: every write goes to a group-commit WAL and is fdatasync'd before it is acknowledged.

02
Latency

The P50 is similar. The P99 shape is not.

Both databases are fast. The difference is in the tail — and in what each design has to do in the background to stay durable. Every VeltrixDB cell below says how it was measured.

Redis numbers above reflect production reports from teams running AOF with appendfsync everysec under mixed read/write load; they are not from a side-by-side run on the same hardware. Your numbers depend on instance size, fork latency, and background save frequency.

!

The GC death spiral — and why VeltrixDB can't get stuck in it. VeltrixDB's own value-log GC backs off when read latency rises, to protect reads. Done naively, that is a spiral: GC pauses, garbage accumulates, reads stay slow, GC stays paused. The GC escalates in three tiers, and at 65% garbage it bypasses the read-pressure pause unconditionally, so it cannot stay paused forever. veltrixdb_vlog_gc_emergency_runs_total counts every time that happens.

03
Storage cost

RAM is 15× more expensive per gigabyte than NVMe.

This math doesn't change. At small scale it doesn't matter. At 100M+ keys, it can be the difference between a few hundred and a few thousand dollars a month. The table below is calculated from list prices and record sizes, not measured.

10M keys · 128B values Redis: ~2.5 GB RAM → r6g.xlarge ~$150/mo
VeltrixDB: ~1.5 GB NVMe → fits on any local-SSD instance
100M keys · 128B values Redis: ~25 GB RAM → r6g.4xlarge ~$1,100/mo
VeltrixDB: ~15 GB NVMe → n2-standard-8-lssd ~$280/mo
1B keys · 128B values Redis: ~250 GB RAM → r6g.metal cluster ~$6,000–8,000/mo
VeltrixDB: ~160 GB NVMe across 3 nodes → ~$900/mo (estimate; 1B keys has not been measured reproducibly)

For batched writes (MultiPut), VeltrixDB's block packing puts up to ~26 records into a single 4 KB VLog block — about 152 B per 128-byte value. A single Put stays on the unpacked path. Storing one record per 4 KB block would waste ~96% of every block; at 1 billion keys that is the difference between roughly 160 GB and 4,096 GB. The DRAM side is separate: the index costs ~64 B per key plus the key itself, and the ordered index for RANGE adds ~90 B per key unless you turn it off with --disable-ordered-index.

If your dataset fits comfortably in RAM and you're not cost-constrained — Redis is the simpler choice. If your keyspace is growing and the RAM bill is growing with it, that's the signal to benchmark VeltrixDB against your workload.

04
Write amplification & SSD wear

Every byte should land on NVMe exactly once.

Write amplification is how many times a byte gets written to storage for every one byte of user data. At 1× you're paying for your data once. At 30× you're paying thirty times — in SSD wear, in NVMe IOPS, and in latency tail.

Redis (AOF rewrite) 2–5× — AOF rewrite rewrites the full dataset to a new file
RocksDB / LevelDB 10–30× — LSM compaction sorts and rewrites every key multiple times across levels
VeltrixDB ~1× by design — values are appended once to the Value Log and never sorted. GC copies still-live values forward when it reclaims a region, so the real figure rises with how much live data GC relocates. Not measured.

VeltrixDB uses WiscKey key-value separation: the per-shard in-memory index (8192 shards) holds only key metadata — offset, disk index, value size, flags, TTL, version. Values go to an append-only Value Log on NVMe. There is no LSM compaction; the value-log GC relocates live values out of mostly-dead regions and skips keys read recently. With a low overwrite rate, write amplification stays close to 1×; heavy overwrites make GC do more copying.

✓

What this means for SSDs (arithmetic, not a benchmark). At 100K writes/sec of 128 B values, 1× write amp writes 12.8 MB/s to NVMe. At 10× (a typical LSM figure) that's 128 MB/s — proportionally more SSD wear and more IOPS to provision.

05
When Redis wins

Redis is the right choice in these situations.

This is not a takedown of Redis. It is the right tool for a large number of workloads. Knowing when not to migrate is as important as knowing when to.

  • Your full dataset fits comfortably in RAM — if you have 5M keys at 256 bytes, Redis's DRAM-only path has zero NVMe latency on any read. The advantage of VeltrixDB's cache tier disappears.
  • You need pub/sub, streams, sorted sets, or Lua scripting — Redis has a rich data structure model built over decades. VeltrixDB is a key-value store. If your application relies on ZRANGEBYSCORE, XREAD, or Lua, stay on Redis.
  • Your team already runs Redis and has no latency complaints — operational familiarity is real value. Don't fix what isn't broken.
  • You need a fully-managed hosted service today — Redis Cloud, ElastiCache, Upstash, and Momento all exist and are production-hardened. VeltrixDB is self-hosted only today; a managed service is planned, not available.
  • Your workload is write-once, read-many and fits in RAM — with no overwrites there is little background rewriting on either side, so VeltrixDB's tail-latency design has little to fix.
06
When VeltrixDB wins

The specific problems VeltrixDB was built to solve.

VeltrixDB earns its place when your dataset is outgrowing your RAM budget, when your production dashboards show Redis P99 spikes you can't explain, or when you're running on Kubernetes with local NVMe and want first-class tooling.

  • Your dataset doesn't fit in RAM — or fitting it costs too much — VeltrixDB's LIRS cache keeps hot keys in DRAM (default -cache 256 MB; size it to your hot set) and a miss costs one pread of a 4 KB VLog block. Your hit rate depends on your access skew — measure it with veltrixdb_cache_hit_rate.
  • Unpredictable P99 under sustained write pressure — if your Redis P99 spikes during AOF rewrite or background save: VeltrixDB never forks, and its admission-controlled three-tier GC is designed to keep background work out of the read tail. That is a design goal; benchmark it on your workload rather than taking a ceiling on faith.
  • High-concurrency bulk writes — MultiPut with 1024-key batches measured 3.54M keys/s (8 clients, 1M-key space, macOS, v1.7) and 1.77M keys/s on a 4-CPU CI runner (tmpfs, same-host client). VLog appends reserve offsets with an atomic add, and a batch is one pwrite plus one fdatasync.
  • Kubernetes with local NVMe SSDs — first-class Kubernetes Operator, Helm chart, and GKE local SSD auto-detection. The nvme-prep DaemonSet formats the local SSDs (XFS) and handles kubelet mount-namespace isolation on GKE/EKS/AKS.
  • Write amplification and SSD cost matter — values are written once and never re-sorted, so there is no LSM-style 10–30× rewrite; GC relocation is the only extra copying.
  • You need predictable latency at scale — not just at P50 — an internal 3-node GKE run (unverified, not reproduced with a published harness) recorded zero GC emergency runs over 30 minutes of sustained 80R/20W load. The reproducible numbers are on the performance page.

08
Migration from Redis

One connection string swap for most workloads.

VeltrixDB's text protocol maps directly to Redis's most common commands (served by the default --net=go front-end). For GET/SET/DEL workloads, switching is a client library change, not an application rewrite.

Try it in 30 seconds

shell — Docker quickstart 
# Linux / Windows
docker run -p 9000:9000 ghcr.io/veltrixdb/veltrixdb:latest

# Mac (Apple Silicon)
docker run --platform linux/amd64 -p 9000:9000 ghcr.io/veltrixdb/veltrixdb:latest

# Test — same semantics as Redis SET/GET
echo -e "PUT hello world\nGET hello\nPING" | nc localhost 9000

SDK migration

Python — before and after 
# Before (redis-py)
import redis
r = redis.Redis(host='localhost', port=6379)
r.set('key', 'value')
val = r.get('key')

# After (veltrixdb-python)
import veltrixdb
r = veltrixdb.Client(host='localhost', port=9000)
r.put('key', 'value')
val = r.get('key')
Node.js — before and after 
// Before (ioredis)
const Redis = require('ioredis')
const r = new Redis({ host: 'localhost', port: 6379 })
await r.set('key', 'value')

// After (veltrixdb-client)
const VeltrixDB = require('veltrixdb-client')
const r = new VeltrixDB({ host: 'localhost', port: 9000 })
await r.put('key', 'value')

VeltrixDB does not speak RESP today, so redis-cli and Redis client libraries will not connect to it. RESP compatibility is on the roadmap, with no date.

✓

Recommended migration strategy. Run VeltrixDB in shadow mode — dual-write to both Redis and VeltrixDB for two weeks, compare read results, validate latency numbers against your actual key distribution. Cutover when the shadow reads match. This is zero-risk and gives you real-world latency data before you commit.
