FAQ

Questions every CTO asks first.

The exact concerns we hear in every initial conversation — answered up front so you don't have to chase them.

Is VeltrixDB a drop-in replacement for Redis or DynamoDB?
Not drop-in. VeltrixDB does not speak the Redis protocol (RESP); it has its own text and binary protocols and client SDKs for Go, Python, Node.js, Java, Rust, and C++. The command set is deliberately familiar — PUT/SET, GET, DEL, HSET/HGET, INCR, CAS, MPUT/MGET, plus ordered scans with RANGE and SCANCUR — so for point-lookup workloads the change is a client swap, not a redesign. If you need joins, SQL, or full-text search, VeltrixDB is the wrong tool — we'll tell you that in the demo.
How fast are reads, really?
The reproducible number: 427,697 reads/s, P99 2.8 ms (avg 461 µs) on YCSB workload C — 100M keys, 200 threads, one AWS node with 4× NVMe. The whole dataset fit in the 400 GB cache, so those were cache hits; we have not published a reproducible run where most reads miss to NVMe, or one at a billion keys. How it works: a sharded, scan-resistant LIRS cache serves hot keys (~92 ns in-process); a miss is one 4 KB-aligned Go pread from the value log, CRC32C-checked; and with no LSM compaction, value-log GC runs off the read path and backs off when read latency rises. Full conditions are on the performance page.
What does the bill actually look like at scale?
VeltrixDB is free and self-hosted, so the bill is your hardware — RAM, NVMe, and network — not a per-operation meter. RAM covers the index (~142 B/key measured at 5M keys with the native index, plus ~90 B/key for the ordered index unless disabled) and whatever cache you choose; NVMe holds the values. See how to size a node, and we'll model your workload during the demo. We don't quote savings percentages we haven't measured.
How does data durability and replication work?
A write is acknowledged only after it is fdatasync'd: the value to the value log and its record to a group-commit WAL, which shares one write(2) and one fdatasync across all writers in the window (15 ms by default). WAL records are binary with a CRC32C over the whole record (binary is the default since v1.6; v1.5 and earlier wrote text records). A crash replays the WAL; a clean shutdown writes a compacted checkpoint. Across nodes: --mode=raft for quorum-committed writes, or --mode=replicated with eventual, quorum, or strong consistency; --rack-id keeps replicas in different zones. Cross-region, repl-ship forwards the change stream. There is no SLA — it's software you run.
What's the security and compliance story?
In the software: AES-256-GCM encryption at rest, TLS 1.3 for clients, mTLS between nodes, RBAC, and an append-only audit log. Because you run it in your own environment, compliance is scoped to your deployment — VeltrixDB itself holds no SOC 2 or ISO 27001 certification. Note that point-in-time-recovery archives hold decrypted values, so protect the archive location.
How long does production migration take?
It depends on how much of your code talks to the store. The usual shape: one helm install, bulk-load with veltrix-migrate (JSONL import/export) or batched MPUT, shadow-read traffic for a few days to validate, then flip the connection. The migration guide walks through dual writes, cutover, and rollback.
What happens when I outgrow a cluster?
Add nodes. The Kubernetes operator reshards when the replica count changes, and the cluster rebalances partitions to the new nodes. There are no plans or capacity tiers to upgrade — the open-source engine has no limits beyond your hardware.
Is VeltrixDB open source? Is there a managed service?
Yes — VeltrixDB is fully open source under Apache 2.0. The server and all core client libraries live on GitHub: clone it, run it, fork it, send PRs. No license keys, no trial limits, no feature-gated tiers — the whole engine is free to use in production. There is no managed cloud service today; VeltrixDB is self-hosted only. A managed service is planned, with no date announced.

Why we built this

Born from a 3 AM page.

VeltrixDB started the night a flash sale buried our Redis cluster under 8 GB of session state. The on-call channel filled with screenshots of P99 climbing past 400 ms. The bill that quarter was already 3× what we'd budgeted.

We tried every workaround you've tried — read replicas, write batching, a DynamoDB migration that ended with a quarter of unpredictable per-op billing. None of it solved the actual problem.

The real problem was structural: keep every value in RAM and the bill scales with your data; use an LSM tree and compaction rewrites your values over and over, taxing NVMe and tail latency exactly when you can least afford it.

So we built VeltrixDB the way we wished a database had been built when we were on call: key–value separation so values are written once, the index in DRAM and the values on NVMe, and open source on your own hardware so the bill never surprises you.

Now we ship it to teams who recognise their own war stories in ours.
