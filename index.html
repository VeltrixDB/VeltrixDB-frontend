The problem
At large key counts, you're not paying for a database. You're paying for RAM.

Redis and other in-memory stores keep every value in DRAM — hot or cold. Cloud RAM costs 15–20× more per gigabyte than NVMe SSD, so the bigger your dataset grows, the more you pay simply to hold it in memory. That's a bill that scales with your data, not your revenue.

Arithmetic from measured per-key costs, not a billion-key benchmark. VeltrixDB’s index takes ~142 B/key (native index, measured at 5M keys) plus ~90 B/key for the ordered index unless --disable-ordered-index, plus whatever cache you give it; a 1 KB value packs into ~1.37 KB of NVMe. An in-memory store holds every value in RAM plus its own per-key overhead. The saving grows with value size: at 128-byte values the index takes about as much RAM as the values do, so small-value workloads save little. Size your own node with the sizing rules.
The shift

One idea, executed properly.

Move the bytes to where they're cheap. Keep only what you need in memory. Never let cleanup touch the fast path.

01 · Storage

Values on NVMe

Written once to an append-only value log. There is no LSM compaction; GC only copies still-live values out of mostly-dead segments — so write amplification stays near 1× by design, not the 10–30× typical of LSM trees.

02 · Memory

Index in DRAM

Only the index lives in memory — ~142 B/key measured — off the Go heap on cgo builds. A read is a cache hit (~92 ns in-process) or one 4 KB-aligned, CRC-checked NVMe read on a miss.

03 · Latency

P99 that holds

Value-log GC runs off the fast path and backs off when read latency rises. In the YCSB run: 100M durable writes and 10M reads, zero failures, read P99 2.8 ms.
