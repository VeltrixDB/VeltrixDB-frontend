Why we wrote it

Open source, documented to the last byte.

VeltrixDB is open source under Apache 2.0 — every line is on GitHub. But reading the Go source isn't how most teams evaluate a database, so we also wrote this architectural document. It's the fastest way for a CTO or security-review team to understand exactly how the engine works — and the source is right there when they want to go deeper.

Key–value separation, end to end.

pread, pwrite and fdatasync — and where io_uring fits.

Reads are one Go pread per cache miss; a write batch is one pwrite and one fdatasync. Why the io_uring write bridge is opt-in (off by default), and what it measured on a 4-CPU CI runner.

03 Durability

The fsync chain, crash replay and checkpoints.

Group-commit WAL (default 15 ms window), why VLog and WAL fdatasync run concurrently, full replay after a crash, the compacted checkpoint written on clean shutdown, and the conditions under which an acknowledged write can be lost.

04 Sharding & placement

8192 index shards · consistent hashing · rack-aware.

One FNV-1a hash drives three placements: 8192 index shards, up to 256 cache shards, and the disk. Cluster routing by consistent hashing, and --rack-id placement that keeps copies of a partition in different racks or zones.

Why LRU lies — and what we replaced it with.

The LIRS algorithm in detail, the priority-2 eviction resistance for small values, and why the cache is split into up to 256 shards (one lock was 21.7% of CPU; a hit went from 711 ns to ~92 ns).

How the engine handles failure.

Crash restart, silent disk corruption, a slow disk, GC falling behind, node loss. For each: what the engine does, which metric shows it, and what is tested today (end-to-end failover, persistence and backup/restore suites).

A sneak peek

The kind of detail you need before you commit.

Two pulled-out figures from the document — the write path, and the failure matrix.

Figure 03 · Write path

Group-commit WAL with amortized fsync.

A PUT is compressed, then encrypted (if enabled), then appended to the VLog and the WAL concurrently. The caller waits for max(WAL, VLog), not their sum. Writers inside one flush window (default 15 ms) share a single write(2) and a single fdatasync; only then is the index entry installed, the cache updated and the write acknowledged.

The chapter covers the binary WAL record (48-byte header, CRC32C over the whole record; the default since v1.6, with --wal-format=text as rollback), crash replay, the compacted checkpoint written on clean shutdown, and the exact conditions under which an acknowledged write survives a single-node crash.

Chapter 7 · sample

Six failure modes and how you'll see them.

A taste of the failure chapter — what the engine does in each case and the Prometheus metric that shows it. Where something is covered by the end-to-end test suites, we say so; we don't quote recovery times we haven't measured reproducibly.

01

Crash restart

A crash (or kill -9) means a full replay of wal.log on start. Writes are acknowledged only after WAL and VLog fdatasync, so an acknowledged write is on disk. A clean shutdown instead writes a compacted checkpoint (one record per live key) and renames it over the WAL. Covered by the persistence e2e suite.

02

Keys the old WAL could not replay

The legacy text WAL truncated replay for keys containing | or a newline, so acknowledged writes could be lost on a crash restart. The binary WAL (default since v1.6) fixes this and reads old text records mixed in.

03

Silent disk corruption

Every VLog record carries a magic number and a CRC32C, checked on every read. A background scrubber walks the log; any mismatch increments veltrixdb_scrub_corruption_total. Any non-zero rate means investigate.

04

A slow or failing disk

Per-disk read and write latency EWMAs are sampled continuously. A disk at ≥ 5× the median raises veltrixdb_vlog_disk_slow. Each disk has its own WAL and VLog, so a failure on one disk does not touch the others.

05

GC falling behind

GC pauses under read pressure, which alone could stall it forever. It escalates in three tiers and at 65% garbage bypasses the pause unconditionally. Each bypass increments veltrixdb_vlog_gc_emergency_runs_total; a persistent rate means writes exceed sustainable GC bandwidth.

06

Node loss

The failure detector marks unresponsive nodes and replicas keep serving, in async, quorum or strong replication or Raft mode. --rack-id keeps copies of a partition in different racks or zones. Covered by the node-failover e2e suite; we don't publish recovery times we haven't measured reproducibly.

Chapter 9 · sample

Engine work, v1.6–v1.7.

Chapter 9 documents the engine changes that shipped in v1.6 and v1.7. Every number states its conditions, including the ones that did not go our way.

01

Off-heap native index

Each shard’s index moves into a C++ table off the Go heap on cgo builds (macOS included). Go’s GC no longer scans it. Measured at 5M keys: full GC 21 → 0.27 ms, settled RSS 168 → 142 B/key, for ~19 ns more per cache-miss lookup. Needs vm.max_map_count ≥ 262144 at large key counts.

02

Binary WAL

48-byte little-endian header, CRC32C over the whole record. Fixes lost writes on crash replay for keys with | or a newline. Encoding 4× faster per record, replay 2.5× faster. --wal-format=text writes the legacy format as a rollback.

03

Ordered-index overwrite fix

Overwriting a live key no longer re-inserts it into the RANGE skiplist. Server batch writes (8 clients × 1024-key MPUT, 1M keys, macOS): 1.45M → 3.54M keys/s, P99 9.6 → 4.2 ms.

04

C++ network front-end — experimental

--net=cpp: an event loop per core, binary protocol only, standalone mode only, opt-in. On a 4-CPU CI runner: read P50 154 vs 286 µs, but read P99 ~3.0 vs 1.8 ms and batch writes ~12% lower. Not faster overall. Disk-bound reads now finish off the loop (deferred reads); not re-measured yet.

05

io_uring write bridge — now opt-in

It used to start on every Linux cgo build. A VLog batch is already one pwrite + one fdatasync, and with the C++ storage extras all on the CI runner measured 1.12M vs 1.77M keys/s batch writes. Per-part attribution is pending; scripts/net-bench.sh bisects it. VELTRIXDB_URING_BRIDGE defaults to off.

—

What is not wired in

cpp/ also holds an ART index, a priority io_uring scheduler, an SQPOLL reader, a C++ VLog and an eBPF GC throttle. They compile, and nothing in Go calls them. The read path is Go pread. The chapter says so explicitly rather than listing them as features.
