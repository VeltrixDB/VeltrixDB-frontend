This run did not measure cache-miss reads. When a read does miss the cache, the value is read with one Go pread of a 4 KB-aligned VLog block, checked with magic + CRC32C. That is not io_uring and not zero-copy. The in-process cache hit itself costs ~92 ns; the rest of the read latency above is spent outside the cache lookup (network round trip, protocol, 200 concurrent clients).

Active Development · September 2026

What we're working on in the engine.

All of this has shipped: v1.6 and v1.7, with v1.8 the latest release. Each item lists what we measured and under which conditions, including the result that did not go our way. No dates are promised.

01
Shipped
Index
Off-heap native index
On cgo builds (macOS included, and the Docker image) each shard’s index lives in a C++ table off the Go heap: 64 B records, 8 B tag|position slots, a per-shard key arena. Go’s garbage collector no longer scans it. The cost is ~19 ns more per cache-miss lookup, and large key counts need vm.max_map_count ≥ 262144. VELTRIXDB_INDEX=map opts out. Since v1.6.

full GC at 5M keys
(was 21 ms)
02
Shipped
Durability
Binary WAL
A 48-byte little-endian header and a CRC32C over the whole record. It fixes a real bug: keys containing | or a newline truncated text-WAL replay, so acknowledged writes could be lost on a crash restart. The reader accepts binary and legacy text records mixed; --wal-format=text is the rollback. Since v1.6.

faster replay
4× faster encode
03
Shipped
Write path
No skiplist re-insert on overwrite
Overwriting a live key no longer re-inserts it into the ordered index; only absent or tombstoned keys are inserted. Measured on server batch writes (8 clients × 1024-key MPUT, 1M-key space, macOS): 1.45M → 3.54M keys/s, P99 9.6 → 4.2 ms.

04
Experimental
Network
C++ network front-end (--net=cpp)
Opt-in, standalone mode only, binary PUT/GET/DEL/PING/MPUT/MGET only. On a 4-CPU CI runner it cut read P50 by ~45% (154 vs 286 µs) and poll read throughput rose 10%, but read P99 got worse (~3.0 vs 1.8 ms), batch writes were ~12% lower and io_uring did not beat poll. It is not faster overall. Since then, reads that need a disk read are finished off the event loop (deferred reads); that change has not been re-measured yet.

Storage
Bisecting the C++ storage layer
On the same runner, the C++ storage extras all on (io_uring write bridge + SQPOLL, batch engine, native index) measured 1.12M keys/s batch writes vs 1.77M with them off. Which part costs what is not known yet; scripts/net-bench.sh runs each engine variant separately to find out. Meanwhile the io_uring write bridge is opt-in (VELTRIXDB_URING_BRIDGE, default off).
