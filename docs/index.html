VeltrixDB Documentation

VeltrixDB is an NVMe-native distributed key-value database. Values live on NVMe in an append-only log with ~1.0× write amplification (WiscKey KV-separation); the index and hot values stay in DRAM. This is the complete reference for building, deploying, and operating it.

What's new in 1.1.0

Lists, sets & HNSW vector search
Two new data types plus a built-in HNSW vector index (VSET / VSEARCH) — persisted, replicated, rebuilt on restart.
Linearizable reads & auto-rebalance
Raft-mode GET behind a ReadIndex fence (--linearizable-reads), and node join/leave now migrates keys automatically.
Durable cross-region catch-up
repl-ship checkpoints its cursor and replays exactly the writes it missed via /admin/changes — deletes included.
PBKDF2 password hashing
210k-iteration PBKDF2-HMAC-SHA256 with per-user salts; legacy hashes keep working with a deprecation warning.
Atomics in every SDK
CAS / INCR / DECR / SETNX now ship in Go, Python, Node.js and Java — matching Rust and C++.
Disk-failure auto-degrade
A per-disk breaker fails writes fast after repeated I/O errors and flips /readyz to degraded so orchestrators drain the node.
Rack-aware replica placement
--rack-id keeps every copy of a partition in a distinct zone; labels propagate via gossip, rackless clusters are unchanged.
Admin API access control
/admin/* is loopback-only by default; --admin-token adds bearer-token auth. Metrics and probes stay unauthenticated.

Why VeltrixDB

Redis keeps everything in RAM — a billion 128-byte keys needs roughly 250 GB of memory, on the order of $3,000–5,000/month in cloud RAM. VeltrixDB keeps values on NVMe and only a 64-byte pointer per key in DRAM, so the same dataset fits in about 160 GB of NVMe for roughly $300–500/month. LSM-based stores like RocksDB typically see 10–30× write amplification from compaction; VeltrixDB's WiscKey-style KV-separation keeps that close to 1.0×.

See the honest trade-offs in Limitations & Roadmap and a feature-by-feature breakdown in VeltrixDB vs. Redis.
