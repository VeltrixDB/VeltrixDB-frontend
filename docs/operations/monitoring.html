Monitoring & Observability

VeltrixDB exposes a Prometheus scrape endpoint (about 85 veltrixdb_* metric families), liveness/readiness probes, a slow-trace endpoint and a web dashboard, all on the same admin HTTP port.

Endpoints

curl http://localhost:2112/metrics   # Prometheus scrape endpoint
curl http://localhost:2112/healthz   # liveness probe ("ok")
curl http://localhost:2112/readyz    # readiness probe ("ready" / 503)
curl http://localhost:2112/traces    # recent sampled + slow (≥ 50 ms) spans, NDJSON
open http://localhost:2112/admin/ui  # web dashboard (loopback-only unless -admin-token)

All of these are served on the admin/metrics port (-metrics-addr, :2112 by default), separate from the client data port (9000 by default). /metrics, /healthz and /readyz are never authenticated. /readyz answers 503 initializing until the engine is open and 503 degraded: disks [N] failed when a disk breaker has tripped; it does not wait for WAL replay or the search-index rebuild — check INFO for search_ready=1 before sending searches to a restarted node.

Only veltrixdb_* series are exported. The server registers its own collector on a private registry: there are no go_* runtime or process_* metrics, and the runtime / process / system / disk collector in metrics/hardware.go is not registered either. Get process and host metrics from node-exporter or a process exporter. Search has no Prometheus metrics; its state is in INFO (search_ready, search_loaded=x/y) and the logs.

Useful PromQL for day-to-day operation:

rate(veltrixdb_storage_writes_total[1m])                            # write throughput
rate(veltrixdb_storage_reads_total[1m])                             # read throughput

rate(veltrixdb_cache_hits_total[5m]) /
  (rate(veltrixdb_cache_hits_total[5m]) + rate(veltrixdb_cache_misses_total[5m])) # hit ratio

rate(veltrixdb_storage_writes_total[1m]) / rate(veltrixdb_storage_wal_flushes_total[1m])  # WAL amortization

histogram_quantile(0.99, rate(veltrixdb_storage_read_latency_seconds_bucket[5m])) # P99 read

Disk-failure auto-degrade

VeltrixDB detects failing disks automatically with a per-disk consecutive-error breaker: 5 consecutive I/O errors on a disk's WAL/VLog trip the breaker and mark the disk FAILED. Any successful I/O before the fifth error resets the streak, so transient hiccups don't trip it. Once tripped:

  • Writes routed to that disk fail fast with ErrDiskFailed ("disk marked FAILED — node is degraded, retry on another replica") instead of hitting the dead device's timeouts. Clients should treat it as a retriable node-degraded condition and retry against another replica.
  • Reads still try the device — data may be partially readable — and are served from cache when possible.
  • GC and compaction skip the failed disk.
  • /readyz returns 503 with a body like degraded: disks [2] failed, so orchestrators (Kubernetes readiness probes) stop routing new traffic to the node while reads keep being served.
  • INFO reports FAILED_DISKS=[2], and the engine's internal DiskFailures counter records breaker trips (it is not exported as a Prometheus series; alert on /readyz or INFO).
The breaker does not auto-reset. A failed disk is never automatically un-failed, even if subsequent I/O would succeed — recovery requires draining the node, replacing the disk, and restarting. See the Disaster Recovery runbook for the exact sequence.

Admin API

The same admin port also exposes a small JSON control-plane API, documented in full in the Admin API reference:

curl    http://localhost:2112/admin/stats       # engine snapshot (JSON)
curl    http://localhost:2112/admin/version     # schema version
curl -X POST http://localhost:2112/admin/checkpoint  # force WAL checkpoint
curl    http://localhost:2112/admin/cdc?prefix= # live CDC events (NDJSON)
curl    http://localhost:2112/admin/cluster     # topology: role, raft term/leader, peers, epoch, replica lag

Grafana dashboards

The repository ships provisioned Grafana dashboards under grafana/ — a Prometheus datasource and dashboard provider under grafana/provisioning/, an operational dashboard (veltrixdb_dashboard.json: throughput, latency percentiles, cache hit rate and evictions, per-disk VLog size and garbage ratio, GC), a larger veltrixdb_complete_dashboard.json, and a CI dashboard (ci_dashboard.json). The runtime, process, system and disk panels query veltrixdb_runtime_* / veltrixdb_process_* / veltrixdb_system_* / veltrixdb_disk_* series from the unregistered hardware collector, so they stay empty against a stock server.

The repository also ships monitoring/servicemonitor.yaml (scrapes port metrics every 15 s on pods labelled app.kubernetes.io/name=veltrixdb in namespace veltrixdb) and monitoring/prometheus-rules.yaml, a PrometheusRule with 10 alerts:

Profiling New in v1.7

Start the server with -pprof-addr=127.0.0.1:6060 to serve CPU, heap, goroutine and execution-trace profiles on a separate listener (never the metrics port):

go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30   # CPU
go tool pprof http://127.0.0.1:6060/debug/pprof/heap                 # heap
curl -o trace.out 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5' # execution trace

When the experimental C++ network front-end (-net=cpp|uring|poll) is in use, the server also logs a per-stage latency report at shutdown (stages iter, cb_enter, exec, put_sched, put_exec, wake, defer_sched, defer_exec; log2 µs buckets).
