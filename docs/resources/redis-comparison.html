VeltrixDB vs. Redis

An honest comparison. Redis is excellent software with a massive ecosystem — VeltrixDB solves a different set of problems. Use this page to decide which one fits your workload.

The fundamental difference

Redis stores everything in RAM. It is fast by default and expensive at scale; with persistence on, fork-based snapshotting and AOF rewrites can cause latency spikes.

VeltrixDB stores values on NVMe SSDs behind a DRAM index and an LIRS cache. Every write is fdatasync-durable. It targets bounded P99 latency under sustained load, packs small values densely on disk (several records per 4 KB VLog block), and its VLog garbage collector escalates to an emergency mode that cannot be paused when garbage passes 65%. Redis has no comparable GC; its persistence-related tail spikes come from the fork behind RDB saves and AOF rewrites.

Storage cost at scale

KeysValue sizeRedis RAM (estimate)VeltrixDB RAM (index)VeltrixDB NVMe (packed values)

Every cell is per-key arithmetic, not a measurement; 1 billion keys has not been measured reproducibly. The VeltrixDB RAM column is the index: about 142 B per key with the native index (measured at 5M keys), plus ~90 B per key for the ordered index unless --disable-ordered-index is set — plus whatever cache you configure. The RAM saving depends on value size. With 128-byte values the index is about as large as the values, so VeltrixDB saves little RAM; with 1 KB values it needs roughly 4–7× less. The NVMe column assumes packed writes (MultiPut, ~26 × 128 B records per 4 KB block); a single Put takes a whole 4 KB block. Price your own configuration rather than relying on a fixed RAM-to-NVMe ratio.

Write amplification

EngineWrite amplificationWhy
Redis (AOF rewrite)periodic full rewriteAOF rewrite rewrites the full dataset
RocksDB / LevelDBcommonly cited 10–30×LSM compaction sorts and rewrites
VeltrixDB~1× by design for packed writes; not measuredEach value is appended once to the Value Log, and a small header + key record to the WAL. Values are rewritten only when VLog GC relocates live values out of a region that is mostly garbage (triggered at 30% dead space by default). A single small Put pads its record to a 4 KB block.

Write amplification maps directly to SSD wear and write latency. Overwrite-heavy workloads pay for it through GC relocation; watch veltrixdb_vlog_garbage_ratio and veltrixdb_vlog_gc_runs_total (veltrixdb_vlog_gc_bytes_total counts bytes reclaimed, not bytes relocated).

When Redis wins

Use Redis when:

  • Your full dataset fits comfortably in RAM — at, say, 5M keys and 256 bytes each, Redis’s DRAM-only path beats any disk-backed system at P50.
  • You need pub/sub, streams, sorted sets, or Lua scripting — Redis has a rich data-structure model; VeltrixDB is a key-value store with hashes, lists, sets, counters, CAS, TTLs, ordered range scans, secondary indexes and multi-key transactions, but none of those four.
  • Your team already runs Redis — operational familiarity has real value.
  • You need a managed hosted service today — Redis Cloud, ElastiCache, and Upstash all exist. VeltrixDB’s managed offering is not yet available.

When VeltrixDB wins

Use VeltrixDB when:

  • Your dataset doesn’t fit in RAM — or fitting it in RAM costs more than you want to pay. VeltrixDB’s LIRS cache keeps hot keys in DRAM; cold keys spill to NVMe automatically.
  • You need predictable P99 under sustained write pressure — VeltrixDB’s GC throttles itself on read latency and escalates in tiers rather than stalling foreground traffic.
  • You’re doing bulk writes at high concurrency — MultiPut with 1024-key batches measured 1.77M keys/s on a 4-CPU CI runner (tmpfs, client on the same host) and 3.54M keys/s on macOS, fdatasync-durable per batch (v1.7).
  • You’re running on Kubernetes with local NVMe — a Kubernetes Operator and a Helm chart (with an nvme-prep DaemonSet for GKE local SSDs) live in separate repositories; the main repository ships the kubectl-veltrix plugin and Prometheus rules.
  • Write amplification matters — append-once values avoid LSM-style compaction rewrites; measure GC relocation for your overwrite rate.

Migrating from Redis

VeltrixDB does not speak RESP, so redis-cli and Redis client libraries cannot connect: migration means changing client code, not a connection string. The text protocol works with nc (served by the default --net=go front-end; the opt-in C++ front-end speaks only the binary protocol):

# Redis
redis-cli SET mykey myvalue
redis-cli GET mykey

# VeltrixDB (SET is accepted as an alias of PUT)
echo -e "PUT mykey myvalue\nGET mykey" | nc localhost 9000

To copy data, veltrix-migrate import --dst host:9000 reads JSONL from stdin, one {"k": key, "v": base64 value} per line; there is no Redis importer, so produce that file yourself (for example with redis-py’s scan_iter + get). It sends one PUT at a time and does not carry TTLs.

For SDK migration, swap the client. The SDKs are maintained in a separate repository and this example was not verified against it; check the Python SDK page for the current API:

# Before (redis-py)
import redis
r = redis.Redis(host='localhost', port=6379)
r.set('key', 'value')
val = r.get('key')

# After (veltrixdb-python)
import veltrixdb
r = veltrixdb.Client(host='localhost', port=9000)
r.put('key', 'value')
val = r.get('key')
Roadmap Redis protocol compatibility (RESP) is on the roadmap but not implemented; today every client must use the VeltrixDB text or binary protocol. See Limitations & Roadmap.

Vector and hybrid search vs. Redis Query Engine
