VeltrixDB vs. Redis

An honest comparison. Redis is excellent software with a massive ecosystem — VeltrixDB solves a different set of problems. Use this page to decide which one fits your workload.

The fundamental difference

Redis stores everything in RAM. It is fast by default and expensive at scale; with persistence on, fork-based snapshotting and AOF rewrites can cause latency spikes.

VeltrixDB stores values on NVMe SSDs behind a DRAM index and an LIRS cache. Every write is fdatasync-durable. It targets bounded P99 latency under sustained load, packs small values densely on disk (several records per 4 KB VLog block), and its VLog garbage collector escalates to an emergency mode that cannot be paused when garbage passes 65%.

NVMe cache-miss read latency has not been measured in a published run. The read path is one 4 KB-aligned Go pread per miss; P99 is kept bounded by the VLog GC throttling on read-latency EWMA (GC capped at 60 MB/s above 15 ms, paused above 20 ms), not by any I/O priority queue. An internal, unverified 3-node GKE run is described on Benchmarking Methodology.

Both columns are estimates, not measurements (the 1B-key disk figure is the projection from BENCHMARKING.md; 1 billion keys has not been measured reproducibly). Note that VeltrixDB still keeps its index in RAM — about 142 B per key with the native index, plus ~90 B per key for the ordered index unless --disable-ordered-index is set — so RAM needs scale with key count, not value bytes. RAM is considerably more expensive per GB than NVMe in cloud pricing; price your own configuration rather than relying on a fixed ratio.

Write amplification

EngineWrite amplificationWhy
Redis (AOF rewrite)periodic full rewriteAOF rewrite rewrites the full dataset
RocksDB / LevelDBcommonly cited 10–30×LSM compaction sorts and rewrites
VeltrixDBlow; not measuredEach value is appended once to the Value Log, and a small key/offset record to the WAL. Values are rewritten only when VLog GC relocates live values out of a region that is mostly garbage (triggered at 30% dead space by default).

Write amplification maps directly to SSD wear and write latency. Overwrite-heavy workloads pay for it through GC relocation; watch veltrixdb_vlog_gc_bytes_total to see how much.

When Redis wins

Use Redis when:

  • Your full dataset fits comfortably in RAM — at, say, 5M keys and 256 bytes each, Redis’s DRAM-only path beats any disk-backed system at P50.
  • You need pub/sub, streams, sorted sets, or Lua scripting — Redis has a rich data-structure model; VeltrixDB is a key-value store.
  • Your team already runs Redis — operational familiarity has real value.
  • You need a managed hosted service today — Redis Cloud, ElastiCache, and Upstash all exist. VeltrixDB’s managed offering is not yet available.

When VeltrixDB wins

Use VeltrixDB when:

  • Your dataset doesn’t fit in RAM — or fitting it in RAM costs more than you want to pay. VeltrixDB’s LIRS cache keeps hot keys in DRAM; cold keys spill to NVMe automatically.
  • You need predictable P99 under sustained write pressure — VeltrixDB’s GC throttles itself on read latency and escalates in tiers rather than stalling foreground traffic.
  • You’re doing bulk writes at high concurrency — MultiPut with 1024-key batches measured 1.77M keys/s on a 4-CPU CI runner (tmpfs, client on the same host) and 3.54M keys/s on macOS, fdatasync-durable per batch (v1.7).
  • You’re running on Kubernetes with local NVMe — VeltrixDB ships a first-class Kubernetes Operator, Helm chart, and GKE local-SSD auto-detection.
  • Write amplification matters — append-once values avoid LSM-style compaction rewrites; measure GC relocation for your overwrite rate.

Migrating from Redis

VeltrixDB uses a simple text protocol compatible with nc:

# Redis
redis-cli SET mykey myvalue
redis-cli GET mykey

# VeltrixDB (same semantics)
echo -e "PUT mykey myvalue\nGET mykey" | nc localhost 9000

For SDK migration, swap the client (the SDKs are maintained in a separate repository; check the Python SDK page for the current API):

# Before (redis-py)
import redis
r = redis.Redis(host='localhost', port=6379)
r.set('key', 'value')
val = r.get('key')

# After (veltrixdb-python)
import veltrixdb
r = veltrixdb.Client(host='localhost', port=9000)
r.put('key', 'value')
val = r.get('key')

The API surface is intentionally close. PUT/GET/DEL map directly to SET/GET/DEL. MultiPut/MultiGet map to Redis pipelines. SETNX, INCR, DECR, and CAS are all supported.

Roadmap Redis protocol compatibility (RESP) is on the roadmap but not implemented; today every client must use the VeltrixDB text or binary protocol. See Limitations & Roadmap.
