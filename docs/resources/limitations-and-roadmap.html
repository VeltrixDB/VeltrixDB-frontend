Limitations & Roadmap

These are real gaps in VeltrixDB today. We'd rather you know them upfront than discover them in production.

Honest limitations

Current as of v1.12 (2026-09-30), checked against the server source. Gaps that are fixed on the main branch after v1.13 are listed under Fixed after v1.13 (next release) — they still apply to a v1.12 install until you upgrade.

Product and ecosystem

No Redis protocol (RESP) You can't point a Redis client at VeltrixDB. Workaround: the text protocol (nc-compatible) or one of the native SDKs; the command surface (PUT/GET/DEL, atomic ops) is close to Redis's. Roadmap: yes; nothing in the code implements it yet.
No managed cloud offering Self-hosted only. Workaround: the Helm chart or Operator (both in separate repositories) on your own cluster. Roadmap: planned.
No same-hardware comparison with other databases yet bench/compare holds a go-ycsb runner with Aerospike and ScyllaDB drivers and a vector benchmark, but the Aerospike / ScyllaDB paths are compile-checked only and nothing has been run side by side. The October 2026 numbers are VeltrixDB-only, mostly on one macOS laptop. Treat any cross-database claim as unmeasured.

Consistency and clustering

RANGE / SCANCUR and namespace scans are node-local They are served from the receiving node's data and do not fan out, so after a rebalance they reflect only that node's keys. (Vector / text / hybrid search, QUERY and IDXQUERY do fan out.) Workaround: fan out and merge client-side.
Replicated mode is not linearizable replicated mode has no single-writer ordering; replicas apply ops in arrival order (version vectors are reserved but unused, no conflict resolution runs). Anti-entropy re-sends un-acked ops only; it never compares keyspaces. --consistency defaults to eventual. Raft and replicated mode are mutually exclusive. In v1.12 a FAILED replica also stays failed until the primary restarts — fixed after v1.13; the fix keeps its catch-up state in memory, so a replica that was down when its primary restarted still misses the writes made before that restart. See Fixed after v1.13. Workaround: raft mode for linearizable writes; on v1.13 and earlier, restart the primary after a replica outage and verify the replica.
Raft is a single group, with a 256 MB snapshot cap One log and one leader, so adding nodes adds fault tolerance, not write throughput. The server snapshot is the whole keyspace as key/value pairs, capped at 256 MB (a larger one is skipped and the log keeps growing), and TTLs are not preserved in it.
Static membership A server builds its membership from --peers at startup; there is no runtime join/drain/remove command, and gossip does not add members. Adding a node means restarting every node with the new --peers list. (In v1.12 tombstone reaping is also not coordinated with replica watermarks — fixed after v1.13.)
Distributed search asks every node Each vector / text / hybrid search, QUERY and IDXQUERY runs on all non-failed nodes, so cost grows with the cluster. A peer that does not answer within --search-timeout-ms fails the request (naming it) until the failure detector marks it failed, unless --search-allow-partial.

Vector and text search

Search indexes are rebuilt at every start The HNSW graphs and BM25 inverted index live in RAM and are not persisted; at startup they are rebuilt from the persisted keys, and searches are refused until that finishes (search_ready=0 in INFO; /readyz does not wait). Budget restart time for large namespaces. Graph nodes, ids and upper layers stay on the Go heap even with GRAPH disk (~280–400 B per vector).
Tested to 100K real vectors Recall and latency are measured on GloVe-100 (100K vectors) and 10K synthetic 768-dim vectors; nothing at 10M+ has been run. Text search has no stemming, phrase queries or per-field weights; one document is at most 1 MiB; dimensions are 1–4096.

Security and data path

No encryption key rotation One key per data dir, loaded at startup, no per-record key version and no re-encrypt command. Changing the key means copying data through a client into a fresh node. See Disaster Recovery.
Audit log is not complete or tamper-evident It records engine writes only (not reads, admin calls, AUTH or TTL expiry), never fills the actor field, drops records when its channel is full, and is not hash-chained. In v1.12 it also covers only single-key PUT/DEL (not batches, transactions or atomic ops) — fixed after v1.13. See Fixed after v1.13. See also Security.
CDC live stream is lossy for slow subscribers /admin/cdc never blocks a writer: a subscriber whose buffer is full loses events and is disconnected (in v1.12 after 3 drops in total; after v1.13, 3 consecutive drops). repl-ship is last-write-wins with no back-pressure to the source. In v1.12 the stream also carries only single-key PUT/DEL — MPUT, coalesced pipelined PUTs, transactions and atomic ops reach a shipper only through the index-backed /admin/changes catch-up (last state only); fixed after v1.13. See Fixed after v1.13.
Backup caveats On v1.13 and earlier the offline veltrixdb-backup must never run against a live server's data dirs (it can truncate them) — use POST /admin/backup or veltrix backup; the next release refuses instead (data-dir lock, see Fixed after v1.13). With --raw-vlogs backups contain no VLog data, and backup does not pause GC. See Backup & Restore.
Monitoring gaps No go_* or process_* metrics (so the shipped restart alert cannot fire) and no search metrics. In v1.12 replication_lag_nanoseconds / cluster_partition_migrations_total are also always 0 — fixed after v1.13. See Fixed after v1.13. See Monitoring.

Engine and front-end

The C++ network front-end is experimental New in v1.7 --net=cpp|uring|poll serves only the binary protocol's PUT GET DEL PING MPUT MGET, only in standalone mode, and refuses --auth-config; the text protocol, AUTH, TLS and every other command stay on the default --net=go. In CI measurements it lowered read P50 but had worse read P99 and ~12% lower batch-write throughput than the Go front-end, so it is opt-in and not faster overall. Workaround: keep --net=go unless you have measured a benefit on your hardware with scripts/net-bench.sh.
Some C++ components are not wired in The ART index, the priority io_uring scheduler, the C++ VLog reader (SQPOLL), the hugepage allocator, mlockall and the eBPF GC throttle exist under cpp/ but have no Go call site, so they do not run. The VLog read path is Go pread. The io_uring VLog write bridge is opt-in (VELTRIXDB_URING_BRIDGE, default off).

Fixed after v1.13 (next release) Fixed on main after v1.13 — ships in the next release

These were gaps in v1.12. They are fixed on the main branch and ship in the next release (no version number yet; v1.13 is still the latest release). Until you upgrade, the v1.12 behaviour described in each item still applies.

  • Data-dir lock. v1.12: never point the offline veltrixdb-backup (or veltrix-repair) at a running server's data dirs — it opens a second engine on the live files, and in testing that produced an empty backup and truncated the live wal.log and vlog_active.dat. Next release: every engine holds an exclusive lock on <data-dir>/LOCK, so a second engine — veltrixdb-backup, veltrix-repair or a second server — is refused with ErrDataDirLocked and the live files are not touched; veltrixdb-backup tells you to stop the server or use POST /admin/backup / veltrix backup. restore / restore-pitr take the same lock.
  • Atomic ops and the value transform. v1.12: CAS/INCR/DECR/SETNX store the raw value (plaintext even under --encrypt-at-rest) and misread a compressed or encrypted value on a cache miss — do not mix them with encryption at rest on the same keys. Next release: they compress and encrypt like PUT. Values written by older builds stay plaintext until their next update.
  • TTLs survive restarts; expired keys are not served from the cache. v1.12: the WAL carries no TTL, so after any restart a TTL'd key comes back without an expiry (and one that had expired comes back), and a cached key could be served after it expired. Next release: a TTL'd key's WAL record carries its absolute expiry (binary record version 2, or an 11th field in the text format); replay restores it and drops keys that already expired; checkpoints, backups and PITR archives carry it; a cache hit past the deadline is not served. Rolling back to an older build: run once with --wal-format=text-legacy and stop cleanly (TTL'd keys become immortal on the older build).
  • MGET returns empty values. v1.12: an empty value written by MPUT reads as missing in MGET. Next release: MGET agrees with GET.
  • CDC and audit cover every write path. v1.12: both see only single-key PUT/DEL, and a CDC subscriber is closed after 3 drops in total. Next release: MPUT, pipelined PUTs, TXN, Raft batch apply and the atomic ops all emit one CDC event and one audit record per key (atomic ops are audited as CAS/INCR/DECR/SETNX, including outcomes that wrote nothing); a subscriber is evicted only after 3 consecutive drops; the audit log is drained and fsynced on shutdown.
  • DEL removes a record's vectors and text documents. v1.12: deleting a KV record leaves @vec/<ns>/<id> and @txt/<ns>/<id> in place, so searches can still return the id — issue VDEL / TDEL as well. Next release: DEL of a record also deletes its vectors and documents in every namespace (crash-safe: the startup rebuild removes any left behind). Vectors and documents that never had a record are untouched; TTL expiry does not cascade.
  • The Raft read barrier covers every read. v1.13 and earlier: only GET and MGET wait for a new leader's no-op (and use the ReadIndex fence with --linearizable-reads); namespace, hash, RANGE/SCANCUR and GETVER reads use local state. Next release: every read on both protocols — namespace, hash, list, set, RANGE/SCANCUR, VER/GETVER, IDXQUERY, QUERY and all searches — passes the barrier.
  • Replication recovers on its own. v1.12: a FAILED replica stays failed until the primary restarts, a node marked FAILED never gets back from RECOVERING to ACTIVE, a full replication write queue drops the op, and tombstones are reaped after the 24 h grace period regardless of replicas. Next release: FAILED replicas are re-probed with backoff (1 s doubling to 30 s) and caught up through SYNC_PENDING before returning to SYNC; a RECOVERING node returns to ACTIVE after 2 good pings; a full queue keeps the op for anti-entropy; tombstone reaping waits for replica watermarks (capped at 2× the grace period).
  • Replication metrics. v1.12: veltrixdb_replication_lag_nanoseconds and veltrixdb_cluster_partition_migrations_total are always 0. Next release: lag is the age of the oldest write a replica has not acked, and migrations count acknowledged key batches; veltrixdb_replication_conflict_resolutions_total and veltrixdb_replication_vector_clock_updates_total (always 0) are removed.
  • CLI. v1.12: veltrix status always prints NOT READY, cdc-tail prints blank fields, flags after the command are ignored, and veltrix and kubectl-veltrix send no admin token, so they work only against servers started without --admin-token. Next release: readiness comes from the /readyz status code, cdc-tail decodes the events, --admin-token / VELTRIX_ADMIN_TOKEN on veltrix, kubectl-veltrix and repl-ship (where it aliases --src-token), flags work after the command, kubectl veltrix quota-set takes --burst, and cache / status / compaction / top / quotas / replication / traces read the right fields.
  • Go client. v1.12: BinaryConn.Put / Pipeline and Client.Put(WithTTL) drop the TTL, and Get returns nil, nil for any server error. Next release: the TTL is sent, Get surfaces server errors and Client.Get follows MOVED; WithConsistency is deprecated (the protocol has no consistency field).
  • Startup banner no longer claims an ART index or io_uring scheduler (neither runs).

Shipped in v1.11–v1.12 New

v1.13 (2026-10-01, documentation and test fixes over v1.12) is the latest release. These used to be roadmap items or gaps:

  • Vector quantization — VCREATE … QUANT int8 (~⅓ of float32 RAM, re-ranked against the stored float32 vectors) and QUANT pq product quantization (v1.12), plus GRAPH disk to move layer-0 graph edges into a memory-mapped file (v1.12). Measured at 768-dim: 3.1× (int8) to 8.9× (PQ + disk graph) less heap per vector.
  • BM25 full-text search (TSET/TDEL/TSEARCH) and hybrid search (HSEARCH, weighted reciprocal rank fusion) with record filters and secondary-index-backed = filters.
  • Cluster search — vector / text / hybrid search, QUERY and IDXQUERY fan out to every node and merge (BM25 with global corpus statistics), failing closed unless --search-allow-partial; derived keys route with their record so filters evaluate locally.
  • HMAC cluster secret (--cluster-secret-file / VELTRIXDB_CLUSTER_SECRET, ≥ 16 bytes) signing all transfer-listener traffic (v1.11).
  • Adaptive group commit (--group-commit=adaptive, default, v1.12): the flush window is an upper bound, so a lone writer is synced at once (emulated 300 µs sync: P50 16 ms → 0.45 ms) and 64 concurrent writers went 4.0K → 37.5K writes/s.
  • Raft read barrier for GET / MGET after leader failover (v1.12) — extended to every other read path after v1.13 (see below).
  • Soak and chaos tests (v1.12) — nightly 20-minute search soak against an oracle, 10 SIGKILL/restart cycles checking every acknowledged write, and GloVe-100 recall gates.
  • Searches are refused during the startup index rebuild instead of silently missing vectors (search_ready in INFO).

Shipped in v1.6–v1.8

  • Off-heap native index on every cgo build (including the Docker image); VELTRIXDB_INDEX=map opts out. Needs vm.max_map_count ≥ 262144 at large key counts.
  • Binary WAL by default, with --wal-format=text for rollback; keys containing | or a newline no longer truncate replay.
  • Ordered-index overwrite skip (server batch writes 1.45M → 3.54M keys/s on macOS).
  • io_uring VLog bridge made opt-in (VELTRIXDB_URING_BRIDGE, default off).
  • Experimental C++ network front-end (--net, --net-threads) with deferred disk reads and a shutdown stage-latency report.
  • --pprof-addr, loadtest --proto, scripts/net-bench.sh, and veltrix-repair.

Shipped in v1.1.0

The following were listed as limitations before the v1.1.0 "distributed-completeness" release and are now implemented — they no longer belong on the list above:

  • Rack/zone-aware replica placement — start each node with --rack-id <zone> and partition placement never puts two copies of a partition in the same failure domain (unless the replication factor exceeds the number of distinct racks, in which case placement still spans every rack available). Rack labels propagate via gossip, and rackless clusters keep the exact previous placement. New in v1.1.0, so less battle-tested than the rest of the placement path. See Cluster & Consensus.
  • Admin API access control — /admin/* now defaults to loopback-only, with an optional bearer token (--admin-token) for remote access. See Security.
  • HNSW vector index — replaced the brute-force scan (reworked in 2026-09; current recall/latency figures are on Vector & Hybrid Search, e.g. GloVe-100 recall@10 0.842 at ef 64 and 0.953 at ef 256).
  • SDK atomics everywhere — CAS/INCR/DECR/SETNX added to the Go, Python, Node.js, and Java clients (previously Rust/C++ only). See the SDK docs.
  • Auto-rebalance — node join/leave/failure triggers ring rebalance and physical key migration; opt out with --auto-rebalance=false.
  • Linearizable reads in raft mode — with --linearizable-reads, GET runs the Raft ReadIndex fence: quorum-confirmed, never stale.
  • List and set data types — LPUSH/RPUSH/LPOP/RPOP/LLEN/LRANGE and SADD/SREM/SISMEMBER/SMEMBERS/SCARD.
  • Distributed routing for all data types — namespace, hash-field, vector, secondary-index, and list/set ops go through the coordinator in raft and replicated modes. Secondary-index definitions now also replicate in replicated mode (as @idxdef/ keys); the local-read gaps above are what's left.
  • Durable cross-DC catch-up — the /admin/changes feed plus repl-ship --checkpoint: a restarted shipper replays exactly the delta it missed before rejoining the live CDC stream. See Replication & CDC.
  • Ordered range scans — RANGE and SCANCUR run over an ordered skiplist of every live key (~90 B/key); point-lookup-only deployments can turn it off with --disable-ordered-index.
  • Raft log snapshots — once the retained log reaches 8192 entries the node writes raft_snapshot.gob and compacts the log; lagging followers catch up via InstallSnapshot.
  • PBKDF2 password hashing — PBKDF2-HMAC-SHA256 (210,000 iterations, per-user random salt) with legacy-hash fallback and a load-time deprecation warning. See Security.

What's coming

From the project changelog's "What's coming" section:

  • RESP protocol (Redis compatibility) — point Redis clients at VeltrixDB without code changes.
  • Managed cloud offering.
  • Multi-region replication with automatic failover — repl-ship ships changes across regions today; failover is manual.
