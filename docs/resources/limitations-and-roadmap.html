Limitations & Roadmap

These are real gaps in VeltrixDB today. We'd rather you know them upfront than discover them in production.

Honest limitations

Current as of v1.12 (2026-09-30), checked against the server source.

Product and ecosystem

No Redis protocol (RESP) You can't point a Redis client at VeltrixDB. Workaround: the text protocol (nc-compatible) or one of the native SDKs; the command surface (PUT/GET/DEL, atomic ops) is close to Redis's. Roadmap: yes; nothing in the code implements it yet.
No managed cloud offering Self-hosted only. Workaround: the Helm chart or Operator (both in separate repositories) on your own cluster. Roadmap: planned.
No same-hardware comparison with other databases yet bench/compare holds a go-ycsb runner with Aerospike and ScyllaDB drivers and a vector benchmark, but the Aerospike / ScyllaDB paths are compile-checked only and nothing has been run side by side. The October 2026 numbers are VeltrixDB-only, mostly on one macOS laptop. Treat any cross-database claim as unmeasured.

Consistency and clustering

The Raft read barrier covers GET and MGET only In raft mode GET and every MGET path wait until a new leader has applied its no-op (and use the ReadIndex fence with --linearizable-reads). Namespace reads (NSGET), hash reads (HGET/HGETALL), RANGE/SCANCUR, namespace scans and GETVER skip it and read local state, which can be stale on followers and briefly on a new leader. Workaround: use GET/MGET for reads that must see every acknowledged write.
RANGE / SCANCUR and namespace scans are node-local They are served from the receiving node's data and do not fan out, so after a rebalance they reflect only that node's keys. (Vector / text / hybrid search, QUERY and IDXQUERY do fan out.) Workaround: fan out and merge client-side.
Replicated mode is not linearizable, and FAILED replicas stay failed replicated mode has no single-writer ordering; replicas apply ops in arrival order (version vectors exist but are unused, no conflict resolution runs). Any failed send marks a replica FAILED, after which replication and anti-entropy skip it until the primary restarts. Anti-entropy re-sends un-acked ops only; it never compares keyspaces. --consistency defaults to eventual. Raft and replicated mode are mutually exclusive. Workaround: raft mode for linearizable writes; restart the primary after a replica outage and verify the replica.
Raft is a single group, with a 256 MB snapshot cap One log and one leader, so adding nodes adds fault tolerance, not write throughput. The server snapshot is the whole keyspace as key/value pairs, capped at 256 MB (a larger one is skipped and the log keeps growing), and TTLs are not preserved in it.
Static membership A server builds its membership from --peers at startup; there is no runtime join/drain/remove command, and gossip does not add members. Adding a node means restarting every node with the new --peers list. Tombstone reaping is not coordinated with replica watermarks (24 h grace period only).
Distributed search asks every node Each vector / text / hybrid search, QUERY and IDXQUERY runs on all non-failed nodes, so cost grows with the cluster. A peer that does not answer within --search-timeout-ms fails the request (naming it) until the failure detector marks it failed, unless --search-allow-partial.

Vector and text search

DEL does not remove a record's vector or text document Deleting the KV record leaves @vec/<ns>/<id> and @txt/<ns>/<id> in place, so the id can still be returned by searches (a filter on the missing record then no longer matches). Workaround: issue VDEL / TDEL as well.
Search indexes are rebuilt at every start The HNSW graphs and BM25 inverted index live in RAM and are not persisted; at startup they are rebuilt from the persisted keys, and searches are refused until that finishes (search_ready=0 in INFO; /readyz does not wait). Budget restart time for large namespaces. Graph nodes, ids and upper layers stay on the Go heap even with GRAPH disk (~280–400 B per vector).
Tested to 100K real vectors Recall and latency are measured on GloVe-100 (100K vectors) and 10K synthetic 768-dim vectors; nothing at 10M+ has been run. Text search has no stemming, phrase queries or per-field weights; one document is at most 1 MiB; dimensions are 1–4096.

Security and data path

No encryption key rotation One key per data dir, loaded at startup, no per-record key version and no re-encrypt command. Changing the key means copying data through a client into a fresh node. See Disaster Recovery.
Atomic ops bypass encryption and compression CAS/INCR/DECR/SETNX store the raw value (plaintext even under --encrypt-at-rest) and misread a compressed or encrypted value on a cache miss. Do not mix them with encryption at rest on the same keys.
Audit log is partial It records only single-key engine PUT/DEL (not batches, transactions, atomic ops, reads, admin calls or AUTH), never fills the actor field, drops records when its channel is full, and is not hash-chained. See Security.
CDC live stream misses batched writes and atomic ops /admin/cdc emits only single-key PUT/DEL; MPUT, coalesced pipelined PUTs, transactions and atomic ops reach a shipper only through the index-backed /admin/changes catch-up (last state only). The stream drops events for slow subscribers and closes a subscription after 3 drops. repl-ship is last-write-wins with no back-pressure to the source.
Backup caveats The offline veltrixdb-backup must never run against a live server's data dirs (it can truncate them) — use POST /admin/backup. With --raw-vlogs backups contain no VLog data, and backup does not pause GC. See Backup & Restore.
Monitoring gaps No go_* or process_* metrics (so the shipped restart alert cannot fire), no search metrics, and replication_lag_nanoseconds / cluster_partition_migrations_total are always 0. See Monitoring.

Engine and front-end

The C++ network front-end is experimental New in v1.7 --net=cpp|uring|poll serves only the binary protocol's PUT GET DEL PING MPUT MGET, only in standalone mode, and refuses --auth-config; the text protocol, AUTH, TLS and every other command stay on the default --net=go. In CI measurements it lowered read P50 but had worse read P99 and ~12% lower batch-write throughput than the Go front-end, so it is opt-in and not faster overall. Workaround: keep --net=go unless you have measured a benefit on your hardware with scripts/net-bench.sh.
Some C++ components are not wired in The ART index, the priority io_uring scheduler, the C++ VLog reader (SQPOLL), the hugepage allocator, mlockall and the eBPF GC throttle exist under cpp/ but have no Go call site, so they do not run. The VLog read path is Go pread. The io_uring VLog write bridge is opt-in (VELTRIXDB_URING_BRIDGE, default off).

Shipped in v1.11–v1.12 New

v1.12 (2026-09-30) is the latest release. These used to be roadmap items or gaps:

  • Vector quantization — VCREATE … QUANT int8 (~⅓ of float32 RAM, re-ranked against the stored float32 vectors) and QUANT pq product quantization (v1.12), plus GRAPH disk to move layer-0 graph edges into a memory-mapped file (v1.12). Measured at 768-dim: 3.1× (int8) to 8.9× (PQ + disk graph) less heap per vector.
  • BM25 full-text search (TSET/TDEL/TSEARCH) and hybrid search (HSEARCH, weighted reciprocal rank fusion) with record filters and secondary-index-backed = filters.
  • Cluster search — vector / text / hybrid search, QUERY and IDXQUERY fan out to every node and merge (BM25 with global corpus statistics), failing closed unless --search-allow-partial; derived keys route with their record so filters evaluate locally.
  • HMAC cluster secret (--cluster-secret-file / VELTRIXDB_CLUSTER_SECRET, ≥ 16 bytes) signing all transfer-listener traffic (v1.11).
  • Adaptive group commit (--group-commit=adaptive, default, v1.12): the flush window is an upper bound, so a lone writer is synced at once (emulated 300 µs sync: P50 16 ms → 0.45 ms) and 64 concurrent writers went 4.0K → 37.5K writes/s.
  • Raft read barrier for GET / MGET after leader failover (v1.12) — see the remaining gap above for other read paths.
  • Soak and chaos tests (v1.12) — nightly 20-minute search soak against an oracle, 10 SIGKILL/restart cycles checking every acknowledged write, and GloVe-100 recall gates.
  • Searches are refused during the startup index rebuild instead of silently missing vectors (search_ready in INFO).

Shipped in v1.6–v1.8

  • Off-heap native index on every cgo build (including the Docker image); VELTRIXDB_INDEX=map opts out. Needs vm.max_map_count ≥ 262144 at large key counts.
  • Binary WAL by default, with --wal-format=text for rollback; keys containing | or a newline no longer truncate replay.
  • Ordered-index overwrite skip (server batch writes 1.45M → 3.54M keys/s on macOS).
  • io_uring VLog bridge made opt-in (VELTRIXDB_URING_BRIDGE, default off).
  • Experimental C++ network front-end (--net, --net-threads) with deferred disk reads and a shutdown stage-latency report.
  • --pprof-addr, loadtest --proto, scripts/net-bench.sh, and veltrix-repair.

Shipped in v1.1.0

The following were listed as limitations before the v1.1.0 "distributed-completeness" release and are now implemented — they no longer belong on the list above:

  • Rack/zone-aware replica placement — start each node with --rack-id <zone> and partition placement never puts two copies of a partition in the same failure domain (unless the replication factor exceeds the number of distinct racks, in which case placement still spans every rack available). Rack labels propagate via gossip, and rackless clusters keep the exact previous placement. New in v1.1.0, so less battle-tested than the rest of the placement path. See Cluster & Consensus.
  • Admin API access control — /admin/* now defaults to loopback-only, with an optional bearer token (--admin-token) for remote access. See Security.
  • HNSW vector index — replaced the brute-force scan (reworked in 2026-09; current recall/latency figures are on Vector & Hybrid Search, e.g. GloVe-100 recall@10 0.842 at ef 64 and 0.953 at ef 256).
  • SDK atomics everywhere — CAS/INCR/DECR/SETNX added to the Go, Python, Node.js, and Java clients (previously Rust/C++ only). See the SDK docs.
  • Auto-rebalance — node join/leave/failure triggers ring rebalance and physical key migration; opt out with --auto-rebalance=false.
  • Linearizable reads in raft mode — with --linearizable-reads, GET runs the Raft ReadIndex fence: quorum-confirmed, never stale.
  • List and set data types — LPUSH/RPUSH/LPOP/RPOP/LLEN/LRANGE and SADD/SREM/SISMEMBER/SMEMBERS/SCARD.
  • Distributed routing for all data types — namespace, hash-field, vector, secondary-index, and list/set ops go through the coordinator in raft and replicated modes. Secondary-index definitions now also replicate in replicated mode (as @idxdef/ keys); the local-read gaps above are what's left.
  • Durable cross-DC catch-up — the /admin/changes feed plus repl-ship --checkpoint: a restarted shipper replays exactly the delta it missed before rejoining the live CDC stream. See Replication & CDC.
  • Ordered range scans — RANGE and SCANCUR run over an ordered skiplist of every live key (~90 B/key); point-lookup-only deployments can turn it off with --disable-ordered-index.
  • Raft log snapshots — once the retained log reaches 8192 entries the node writes raft_snapshot.gob and compacts the log; lagging followers catch up via InstallSnapshot.
  • PBKDF2 password hashing — PBKDF2-HMAC-SHA256 (210,000 iterations, per-user random salt) with legacy-hash fallback and a load-time deprecation warning. See Security.

What's coming

From the project changelog's "What's coming" section:

  • RESP protocol (Redis compatibility) — point Redis clients at VeltrixDB without code changes.
  • Managed cloud offering.
  • Multi-region replication with automatic failover — repl-ship ships changes across regions today; failover is manual.
Track progress Follow GitHub Releases for updates on these items as they ship.
