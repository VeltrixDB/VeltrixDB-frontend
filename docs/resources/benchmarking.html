Benchmarking Methodology

How VeltrixDB's benchmark numbers are produced: the harness, the hardware, the pass/fail gates, and the raw results with the conditions they were measured under — so you can reproduce them or run the same harness against your own workload shape.

The harness

scripts/bench.sh runs a 6-phase sequenced workload (build + start, MPUT bulk load, cool-down, read-only, mixed 70R/30W, sustained MPUT write stress) and reports go/no-go on two hard gates: packing density and GC emergency runs. The project re-runs it after any storage engine change.

It builds the server and loadtest with CGO_ENABLED=0 (Go map index) unless you export CGO_ENABLED=1. The Docker image is a cgo build (native index), so set CGO_ENABLED=1 on Linux to measure what the image runs.

# macOS / Linux dev (uses /tmp, 1M keys)
./scripts/bench.sh

# Linux production-class (n2-highmem-64, 8 NVMe disks)
DATA_DIRS=/mnt/nvme0,...,/mnt/nvme7 \
RAW_VLOGS=/dev/nvme0n1,...,/dev/nvme7n1 \
CACHE_MB=409600 NUM_KEYS=10000000 \
CONCURRENCY=512 BULK_DUR=120 STRESS_DUR=300 \
  ./scripts/bench.sh

Pass criteria

The harness enforces two hard gates. A benchmark run that fails either gate is not representative of the storage engine operating correctly.

GateConditionWhat failure means
Densitybytes/record ≤ 1.2 × (24 + value_size) (veltrixdb_vlog_file_bytes / Δveltrixdb_storage_writes_total after the bulk load)Packing not engaged — keep BATCH_SIZE > 1 (loadtest --batch-size)
GC emergencyveltrixdb_vlog_gc_emergency_runs_total delta == 0 during the write stressWrite rate exceeds GC throughput

The script exits non-zero if either gate fails. It also prints the read P99, but that is not a gate.

Network front-ends and storage configurations (net-bench.sh) New in v1.7

scripts/net-bench.sh starts a fresh server per combination and runs batch write (8 × 1024-key MPUT, BATCH_DURATION, default 10 s), read (64 binary GET clients) and mixed (70/30) workloads, then prints one markdown table (also to $GITHUB_STEP_SUMMARY). The “Net front-end” GitHub workflow runs it on Linux, where the io_uring code exists.

# Front-ends (NET:N = N event loops for a C++ front-end)
NETS="go uring poll uring:2" ENGINES=native WINDOWS=5 ./scripts/net-bench.sh

# Storage configurations under the Go front-end
ENGINES="native bridge sqpoll map nocgo" NETS=go WINDOWS="5 1" ./scripts/net-bench.sh

Defaults: NETS="go uring", ENGINES=native, WINDOWS=5, DURATION=15 s per read/mixed workload, NET_THREADS = CPU count. The C++ front-ends need the binary protocol, so reads and mixed run with loadtest --proto=binary.

ENGINES valueConfiguration
nativeNative C++ index, io_uring VLog bridge off — the default build
inlinenative, but the C++ front-end reads disk on its loop thread (VELTRIXDB_NET_DEFER_READS=0)
bridge / sqpollnative + VELTRIXDB_URING_BRIDGE=on / sqpoll
mapGo map index, bridge off
nocgoVELTRIXDB_DISABLE_CGO_ENGINE=1: map index, no C++ storage layer
  • Every overwrite appends to the WAL and VLog and nothing reclaims space during a run; one combination leaves ~5–10 GB, so each data dir is deleted when its combination finishes.
  • Each workload runs under a watchdog (duration + WATCHDOG_SLACK, default 60 s). On a hang the script dumps native and Go stacks, records a FAILED row, and moves on.
  • C++ front-ends log per-stage latency at shutdown (log2 buckets, so p99<=8ms means [4, 8) ms). A high cb_enter means loop threads are waiting for a Go P; try fewer loops (uring:2).
  • On macOS only poll with one loop runs, and loopback caps round trips at ~60K/s for both front-ends — measure on Linux.

Durable single-key writes: adaptive vs fixed group commit

--group-commit=adaptive (the default since v1.12) vs fixed. The device’s fdatasync cost is emulated (a sleep before the real sync), because macOS fsync returns at the drive cache; that is what makes the result mean the same on a laptop as on Linux. 15 ms window, 128 B values, each writer doing sequential durable Puts for 1.5 s.

VELTRIX_GC_TABLE=1 go test ./storage -run TestGroupCommit_LatencyTable -v

The nightly workflow runs a 20-minute soak and 10 crash cycles on Linux:

VELTRIX_SOAK_DURATION=20m go test ./tests/integration/ -run TestSearchSoak -v -timeout 40m
VELTRIX_CHAOS_CYCLES=10 go test ./tests/integration/ -run TestSearchCrashRecovery -v -timeout 25m

Writes in flight at the kill are not checked. After each crash cycle the test rewrites every id whose write had an unknown outcome to a fresh, fully acknowledged version, so later cycles check those ids too.

Against Aerospike and ScyllaDB (same hardware)

No shared run yet The harness exists; no same-hardware comparison has been run or published. The Aerospike and ScyllaDB drivers (upstream go-ycsb code), docker-compose.yml and aerospike.conf are compile-checked only. There is no vector driver for Aerospike Vector Search or ScyllaDB vector search.

bench/compare/compare.sh runs go-ycsb workloads through a VeltrixDB driver and go-ycsb’s Aerospike and Cassandra (ScyllaDB) drivers, one database at a time on the same machine, and writes results/<ts>/summary.md.

# On the machine under test (Linux, NVMe), with Docker and Go ≥ 1.25:
export BENCH_DATA=/mnt/nvme0/bench BENCH_CPUS=8 BENCH_MEM=16g
./compare.sh                                   # all three, workloads a b c f
RECORDS=10000000 OPS=10000000 THREADS=128 WORKLOADS="a b c d f" ./compare.sh

# Vectors (VeltrixDB only):
../../scripts/ann-dataset.py glove-100-angular /mnt/nvme0/ann --train 1000000 --test 1000
VECTORS=1 ANN_DIR=/mnt/nvme0/ann VEC_ARGS="-quant pq -graph disk" ./compare.sh

Publish a result only with all of these stated next to it: the same machine and disk with one database running at a time (a client on a second machine is better still); the durability setting of each (VeltrixDB ACKs after fdatasync of WAL and VLog; ScyllaDB’s default commitlog_sync: periodic ACKs before the write is on disk, so use batch or report both; Aerospike ACKs from its write buffer); warm-up and a dataset larger than the caches if the point is disk performance; replication factor 1; and the versions of all three.

VeltrixDB vs. Redis, head to head

The VeltrixDB column is from the YCSB run above. The Redis column was not measured — it is a range of commonly cited figures, included for orientation only.

ModeVeltrixDBRedis
Durable writes (fsync every write)18,064 ops/sec10,000–30,000 ops/sec

VeltrixDB always writes durably. Redis requires appendfsync always for an equivalent guarantee, which reduces Redis to 10K–30K ops/sec — comparable to or slower than VeltrixDB at that durability level.

Key takeaways

  • Writes: 18,064 durable writes/sec across 4 NVMe disks at a 5 ms window, zero failures across 100M operations.
  • Reads: 427,697 reads/sec at 461 µs average latency, with the whole dataset in the 400 GB cache (100% hits). Cache-miss (NVMe) read performance was not measured in this run.
  • Disk footprint: 100M keys used ~25 GB per disk out of 873 GB available. Larger key counts (1 billion+) have not been measured reproducibly; note the index itself stays in RAM (~142 B/key with the native index).
  • Durability: every write is crash-safe (WAL + fdatasync). Redis needs appendfsync always for a comparable guarantee.
  • Read hit rate: 100% with proper dataset sizing (recordcount matching operationcount), zero NOT_FOUND across 10 million reads.
Reproduce it yourself The YCSB numbers come from YCSB 0.17.0 against VeltrixDB v1.0 (June 2026); the later measurements from scripts/net-bench.sh and engine benchmarks (September 2026, v1.7 code); the October 2026 tables from the Go tests and bench/compare commands printed above each (v1.11–v1.12 code, macOS laptop); the reference tables from scripts/bench.sh and projections. Re-run the harness against your own key/value shape rather than assuming these numbers transfer directly — see VeltrixDB vs. Redis for how to interpret the results relative to your workload.
