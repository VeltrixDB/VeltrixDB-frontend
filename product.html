Architecture

Fast, simple, and it just works.

All the complexity is hidden. You write data. You read data. Here is exactly what happens in between — the step labels are the mechanism, not timings.

PATH 01 / 03 — DURABLE WRITE

Value lands on NVMe before ack.

The value is appended to the VLog and its pointer to the WAL at the same time; the two fdatasyncs race, so you wait for the slower one, not the sum. The group-commit WAL shares one write(2) and one fdatasync across every writer in the batch. Group commit is adaptive by default (since v1.12): a lone writer is synced at once, and the 15 ms window is only an upper bound. Records are binary with a CRC32C over the whole record.

PATH 02 / 03 — CACHE READ

Hot key served in microseconds.

The sharded LIRS cache is scan-resistant: small hot values (≤256 B) resist eviction, so they stay warm through large cold scans. A hit does no disk I/O. A miss checks the shard's Bloom filter and index, then does one 4 KB-aligned pread from the VLog and verifies magic + CRC32C.

Key marked dead, instantly durable.

Delete follows the same group-commit WAL path as a write. A tombstone is stamped in the index shard. The VLog value is marked dead for the next GC pass — no immediate disk rewrite.

Under the hood

Not a wrapper. A storage engine, rebuilt.

We didn't put a faster cache in front of a slow database. We built the storage layer around one bet — separate keys from values — and then took the index off the garbage collector's plate.

01
Storage engine

Key–value separation, WiscKey-style.

LSM trees rewrite values over and over as compaction merges levels — typically a 10–30× write amplification tax on NVMe endurance and tail latency. We split keys from values.

Each of the 8192 index shards holds a 64-byte record per key — disk offset, size, TTL, version. Values live in an append-only VLog on NVMe, one per disk, written once; there is no LSM compaction. Value-log GC runs in the background, copies only still-live values out of mostly-dead segments, and throttles itself when read latency rises — it is off the read path.

That makes write amplification close to 1× by design — the only rewrite is GC relocating live data. We have not published a write-amplification measurement; the performance page lists what we have measured and under which conditions.

02
Memory & I/O · native index since v1.6

An index the garbage collector never scans.

A Go map holding hundreds of millions of index entries is something the GC has to walk. Since v1.6 the index lives off the Go heap entirely.

Since v1.6: on cgo builds (Linux and macOS, and the Docker image) each shard's index is a C++ table — 64-byte records, 8-byte tag/position slots, a per-shard key arena, large arrays individually mmap'd. Measured with 5M keys: full GC 21 ms → 0.27 ms, settled RSS 168 → 142 B/key, for ~19 ns more per cache-miss lookup. VELTRIXDB_INDEX=map opts out; CGO_ENABLED=0 builds keep the Go map. Hosts need vm.max_map_count ≥ 262144 at large key counts.

The rest of the hot path is deliberately plain. Reads are a Go pread, 4 KB-aligned, checked against magic + CRC32C. VLog batches are one contiguous pwrite and one fdatasync; the WAL flusher does one write(2) per group-commit batch. An io_uring bridge for VLog batch writes exists but is opt-in and off by default (VELTRIXDB_URING_BRIDGE): with a batch already down to one pwrite, it saves at most one syscall. The full picture is in the technical whitepaper.

03
Engine work · v1.6–v1.12

What shipped, and what didn't pay off.

v1.6 through v1.12 carry engine changes we measured — including one that did not pay off overall. v1.12 (2026-09-30) is the latest release.

Binary WAL (default since v1.6). 48-byte header, CRC32C over the whole record. Keys containing | or a newline no longer cut replay short — with the old text format, an acknowledged write after such a key could be lost on a crash restart. Encoding is 4× faster per record, replay 2.5× faster; old text WALs still replay. Ordered index: overwrites of a live key no longer re-insert into the skiplist — server batch writes went from 1.45M to 3.54M keys/s (8 clients × 1024-key MPUT, 1M keys, macOS).

Adaptive group commit (default since v1.12). The WAL and VLog flush windows became upper bounds: a lone writer is synced at once, concurrent writers after an idle gap of about one fdatasync; --group-commit=fixed restores the full-window wait. With an emulated 300 µs fdatasync on a macOS laptop (15 ms window, 128 B values): one writer’s P50 went from 16 ms to 0.45 ms, and 64 writers from 4.0K to 37.5K durable writes/s at P99 2.6 ms. It has not yet been measured on Linux NVMe. Raft read barrier (v1.12): a newly elected leader now waits for its no-op before serving local reads, and MGET passes the same barrier as GET.

C++ network front-end (experimental, opt-in). --net=cpp|uring|poll runs one event loop per core for the binary PUT GET DEL PING MPUT MGET commands, standalone mode only; reads that need disk are handed to goroutines. On a 4-CPU CI runner (measured before disk reads moved off the loop) it lowered read P50 (154 vs 286 µs) but had a worse read P99 and ~12% lower batch-write throughput than the default Go listener. It does not serve the search commands. It is not faster overall, so --net=go stays the default.

Vector, full-text & hybrid search · v1.11–v1.12

Semantic search next to the record it describes.

One id names one record: PUT doc-42 {"lang":"en"}, VSET doc-42 NS docs ... and TSET doc-42 NS docs TEXT ... are the same thing. Vectors and documents persist as ordinary keys, acknowledged after the same WAL + VLog fdatasync as any write; the search indexes in RAM are derived from them. v1.11 shipped int8 quantization, BM25, hybrid search, cluster fan-out, VDEL and vector namespaces; v1.12 added product quantization and the on-disk graph.

01 — RAG retrieval

Chunks, metadata and embeddings under one key.

Store each chunk’s text and metadata as a KV record and its embedding under the same id with VSET. At question time: VSEARCH top-k, MGET the texts, build the prompt. One write path, one WAL, one backup. The repo ships a runnable example (examples/rag_semantic_search.py).

02 — Semantic + keyword

Hybrid ranking without a second system.

TSET indexes a document for BM25; HSEARCH runs the vector and text searches and fuses them by weighted reciprocal rank (ALPHA = vector weight, default 0.5). Ranks, not raw scores, are fused, so cosine and BM25 never need a common scale.

03 — Filtered search

Filter on the record, not a copy of it.

FILTER field op value (= != > < >= <= contains) is evaluated on the KV record whose key is the vector id. An = filter on a field with an IDXCREATE index is served from the index; other filters are checked during the graph walk.

Profiles and nearest neighbours in one call path.

When the same service already does point lookups on user or item records, the similar-items query can hit the same cluster: vectors are routed to the node that owns their record, and in raft or replicated mode a search runs on every live node and is merged.

04
How search works

HNSW in RAM, exact re-rank from NVMe.

Each namespace has one HNSW graph (cosine similarity; M = 16, efConstruction = 200, ef 64 by default, tunable per query with EF). The full float32 vectors always live in the value log; how much of them RAM holds is a per-namespace choice.

Memory layouts (VCREATE ns dim QUANT none|int8|pq GRAPH memory|disk), measured as Go heap per 768-dim vector over 10K vectors on macOS: float32 3,383 B; int8 1,078 B, top 4 × k candidates re-ranked from disk; PQ (m = 96) 493 B, the whole beam re-ranked; PQ + GRAPH disk 378 B of heap plus 216 B in a memory-mapped file the kernel can page to NVMe. The re-rank reads the candidates’ float32 vectors with one parallel MultiGet.

Text and hybrid: Okapi BM25 (k1 = 1.2, b = 0.75) over lowercase runs of Unicode letters and digits — Indic scripts stay whole; no stemming, stop words or phrase queries. HSEARCH fuses with RRF, score = α/(60 + rank_vec) + (1 − α)/(60 + rank_text). Clusters: searches fan out to every non-failed node and merge; BM25 sums every node’s statistics first. A peer that misses --search-timeout-ms (2000) fails the request and is named, unless --search-allow-partial. The node-to-node listener is signed with HMAC-SHA256 via --cluster-secret-file, or use mTLS; without either the server warns it is unauthenticated.

What it won’t do yet: the graph and inverted index are rebuilt at every start and searches are refused until that ends; tested to 100K real vectors and 10K at 768-dim, nothing at 10M+; one graph per namespace, cosine only, no GPU; DEL removes the record but not its vector or text — use VDEL / TDEL too; the search API is in the bundled Go client only (other languages use the text protocol), and the --net=cpp front-ends do not serve it.

Where it fits

Built for teams where microseconds move money.

We don't pretend to be a general-purpose database. VeltrixDB is a point-lookup engine first — if you're running one of these workloads at scale, this was built for you.

01 — AdTech & Real-Time Bidding

User profile lookups inside the 50ms RTB budget.

Fetch the user profile, score the bid, write the impression — at high request rates. Point lookups are the entire workload. Your RAM budget and bare-metal NVMe match the architecture perfectly.

02 — HFT & Crypto Exchanges

Sharded architecture, durable state.

Position state and risk checks that must survive a restart. 8192 index shards keep lock contention low, every write is fsynced before the ack, and CAS / INCR are shard-locked and safe under concurrency. Measure your own tail before you put it on a latency-critical path.

03 — Persistent caches & session stores

Redis-class speed, without RAM-class bills.

When your dataset has outgrown the budget of "keep everything in RAM," but hot keys still need to be served from memory. A DRAM index over NVMe values holds far more data per dollar of RAM — persistent and durable, rebuilt from the WAL checkpoint on restart.

04 — Fraud detection & rate limiting

Continuous writes, instantaneous lookups.

Stream transactions in, score them against history, decide fast. Values are written once, with no LSM compaction rewriting them, so NVMe endurance survives the write rate; batched MPUT keeps ingest cheap.

Honest fit check

What it won't do — and what it needs.

We'd rather lose the deal than oversell. VeltrixDB is a scalpel, not a Swiss Army knife — here's the truth about hardware, query patterns, and memory before we get on a call.

Hard requirements we won't bend on.

Last updated · October 2026
⚠
Bare-metal NVMe or local SSD only
Optimised for direct-attached NVMe on Linux (O_DIRECT, raw block devices supported). Not recommended for AWS EBS, Azure managed disks, or any network-attached storage — they break the latency model.
⚠
Point lookups first
Purpose-built for high-throughput GET / PUT / DEL at scale. Ordered scans exist (RANGE, SCANCUR, backed by a skiplist at ~90 B/key), and so do vector, BM25 and hybrid search — but no joins, no SQL, and no facets or aggregations. No Redis (RESP) protocol — clients use our text or binary protocol and SDKs.
⚠
RAM budget for the index
Every key's index record lives in DRAM. The native index measured ~142 B/key settled RSS at 5M keys (168 B/key with the Go map), plus ~90 B/key for the ordered index unless you pass --disable-ordered-index, plus your cache. Size with your own key lengths — you will not run a large keyspace on a t3.medium.
⚠
Search indexes live in RAM
HNSW graphs and the BM25 index are in memory (~0.4–3.4 KB per 768-dim vector, by layout) and are rebuilt at every start; searches are refused until the rebuild ends. Tested to 100K real vectors — nothing at 10M+ yet.
⚠
Kubernetes pieces are separate repos
The Helm chart (VeltrixDB-Helm-Chart) and the operator (VeltrixDB-Kubernetes-Operator) are published from their own repositories, not the server’s; check their own docs for what each version deploys. Adding a node means every node must list it in --peers — gossip does not add members.
⚠
Encryption has known gaps
--encrypt-at-rest encrypts values (AES-256-GCM), not keys. There is no key rotation: one key per data directory, loaded from an env var or file. Point-in-time-recovery archives hold values decrypted, so protect that location.
Linux for production (macOS fsync is not power-loss safe) · x86-64-v2 CPU baseline on amd64 cgo builds · vm.max_map_count ≥ 262144 for the native index · 3 nodes for replicated production Talk to an architect before you commit →
